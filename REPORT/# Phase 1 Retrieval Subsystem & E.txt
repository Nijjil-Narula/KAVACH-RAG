# Sub-Part 1.1: Multi-Standard Corpus Ingestion & Golden Dataset Construction

Sub-Part 1.1 builds the deterministic data backbone of the cybersecurity RAG pipeline. A retrieval engine is fundamentally bounded by the structural fidelity of its data ingestion: naive chunking truncates JSON brackets, obscures version boundaries, and detaches mitigations from vulnerability identifiers.

This sub-part addresses two deliverables:
1. **The Ingestion Engine:** Converting disparate cybersecurity source repositories into clean, metadata-enriched chunks using format-specific structural splitters.
2. **The 150-Question Golden Evaluation Benchmark:** Engineering an adversarial, mathematically distributed evaluation suite with strict ground-truth lineage to enable independent retrieval and generation scoring.
---

### 1. Deep Dive: The Multi-Standard Ingestion Corpus
The corpus aggregates three industry-standard cybersecurity knowledge sources. Each source serves a distinct role in the system's operational scope, stress-tests a specific architectural layer, and directly validates key evaluation criteria.

```
             │                                  │                                    │

                          ┌─────────────────────────────────┐
```

#### Source 1: NIST National Vulnerability Database (NVD) / CVE Records
* **Format:** Nested JSON objects (`cve.org` / NIST schema 5.0).
* **Structural Reality:** Contains nested arrays for `descriptions`, `metrics.cvssMetricV31` (base scores, vector strings like `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`), and `configurations.nodes.cpeMatch` criteria (criteria strings representing vulnerable version boundaries like `< 4.0.0-rc.2`).
* **Why It Is Essential for the System:**
It provides the ground truth for atomic, high-consequence vulnerability lookups. Security engineers query specific CVEs to determine exploitation vectors and remediation urgency.
* **The Architectural Stress Test:**
Standard character/token splitters routinely split right down the middle of a CVSS JSON object, detaching the base score (`9.8`) from the CVE ID (`CVE-2024-XXXX`), or cutting off the `<` version boundary symbol.
* **Ingestion Strategy (`RecursiveJsonSplitter`):**
The raw JSON is processed using a recursive JSON splitter configured with `max_chunk_size=512` tokens. The splitter treats the JSON tree hierarchically, ensuring that the `cve_id`, `cvss_score`, `vector_string`, and `affected_versions` array are never severed across chunks.

#### Source 2: MITRE ATT&CK Enterprise Matrix
* **Format:** Hierarchical Markdown documents, YAML schemas, and STIX 2.1 JSON definitions.
* **Structural Reality:** Organized around structural trees: **Tactics** (e.g., `TA0001: Initial Access`) $\rightarrow$ **Techniques** (e.g., `T1190: Exploit Public-Facing Application`) $\rightarrow$ **Sub-Techniques** $\rightarrow$ **Mitigations** (e.g., `M1041: Defensive Software`).
* **Why It Is Essential for the System:**
It enables multi-hop reasoning. Real incident response queries are rarely single-step: an analyst will ask, *"What MITRE technique describes the attack vector used in CVE-2024-XXXX, and what enterprise mitigations apply?"*
* **The Architectural Stress Test:**
If a Markdown splitter splits by raw paragraphs, a sub-technique is detached from its parent header. The model receives a chunk saying *"Apply strict input validation"* without the context of which tactic, technique ID, or operating platform it belongs to.
* **Ingestion Strategy (`MarkdownHeaderTextSplitter`):**
Ingested using Markdown header splitting locked to explicit header levels:
`[("#", "tactic"), ("##", "technique_id"), ("###", "mitigation")]`.
The chunk text inherits its parent breadcrumb metadata path automatically:
`metadata={"tactic": "TA0001", "technique_id": "T1190", "type": "mitigation"}`.

#### Source 3: OWASP Top-10 for Large Language Model Applications (v1.1 vs. v2.0)
* **Format:** Comparative Markdown documentation detailing enterprise LLM security guidelines.
* **Structural Reality:** Contains shifting vulnerability definitions between version releases. For instance:
* In **v1.1 (2023)**, `LLM01` represented *Prompt Injection*, while `LLM03` was *Training Data Poisoning*.
* In **v2.0 (2025/2026 update)**, entries were re-indexed and merged, moving *Supply Chain Vulnerabilities* to `LLM03` and adjusting definitions for *System Prompt Leakage* and *Vector/RAG Hallucinations*.

* **Why It Is Essential for the System:**
It acts as the primary evaluation anchor for detecting **contradictory context handling** and **temporal drift**. A production cybersecurity RAG must not blend version standards into a single answer.

* **The Architectural Stress Test:**
If chunks from v1.1 and v2.0 share high semantic similarity, a standard bi-encoder will pull both into the same top-$k$ window. The generator must distinguish the version boundaries and output an explicit distinction rather than hallucinating an inaccurate unified answer.
* **Ingestion Strategy (Version-Enriched Markdown Parsing):**
During document loading, an explicit metadata schema flag (`standard_version: "v1.1"` or `standard_version: "v2.0"`) is injected directly into each chunk's header and vector payload.

### 2. Standardized Chunking Schema & Storage Specification
Every document passed into the ingestion pipeline is parsed into an identical, validated structure before serialization. This schema ensures that downstream retrievers (FAISS and Ettin) receive consistent payload metadata.

#### The Target Document Schema
```json

  "chunk_id": "CVE-2024-3094_chunk_001",
  "document_type": "CVE_RECORD",
  "source_file": "nvd_cve_2024_3094.json",
```

#### Chunking Window Parameters
* **Primary Chunk Size:** **384 to 512 tokens**. (Optimized to fit comfortably within the 512-token input window of the `codefuse-ai/F2LLM-v2-0.6B` bi-encoder without semantic truncation).
* **Chunk Overlap:** **64 tokens** (12.5% overlap). Prevents loss of boundary context across adjacent sections.
* **Serialization Store:** The processed text chunks and associated metadata dictionaries are written to an append-only Apache Parquet table (`corpus_chunks.parquet`). Parquet offers fast columnar I/O, strict type enforcement, and low disk usage compared to raw JSON or SQLite.

1. **60 Factual Lookups (Direct Single-Chunk Lookups):**
* *Target:* Tests baseline semantic retrieval and numerical fidelity.

* *The Test:* Irrelevant or external queries (e.g., *"How do I bake a sourdough loaf?"*, *"Who won the 2024 World Cup?"*, or unindexed proprietary security questions).

* 10 Malformed Inputs & Engineering Typos:
* *The Test:* Real-world engineering shorthand, truncated strings, and degraded inputs (e.g., *"cvs 9.8 vuln xz util liblzma bckdoor mitgation"* or *"cve2024-3094 atack vectr"*).
* *Expected Behavior:* The intent router and bi-encoder must parse through degraded spelling and correctly route to the appropriate CVE/MITRE document.
* 10 Context-Noise / Very Long Queries:
* *The Test:* Verbose, multi-sentence queries surrounded by peripheral system logs, stack traces, and text clutter.
* *Expected Behavior:* The bi-encoder and cross-encoder must filter out token noise to locate the core security question without diluting retrieval similarity.

### 2. Tier 1: AgentIntentRouter (~66M Parameters)
Standard RAG architectures route every prompt through dense vector searches, which wastes CPU cycles on queries that contain exact CVE codes or obvious out-of-scope text. Tier 1 acts as a deterministic pre-retrieval triage layer.

#### 1. Dual-Track Routing Mechanics
The router combines deterministic pattern matching with a lightweight sequence classifier (`microsoft/deberta-v3-small`, 66M parameters):
* **Track A — Deterministic Pattern Matcher (Regex Fast-Path):**
* Evaluates incoming text against compiled regex patterns for security identifiers:
* CVE: `r"^CVE-\d{4}-\d{4,7}$"`
* CWE: `r"^CWE-\d{1,5}$"`
* MITRE: `r"^(T\d{4}(\.\d{3})?|TA\d{4}|M\d{4})$"`
* If a user submits an exact identifier (e.g., *"CVE-2024-3094"*), the router marks it as `FAST_PATH_EXACT_LOOKUP`. It skips vector math completely and pulls the document directly from `corpus_chunks.parquet` using indexed hash keys in under 1 millisecond.
* **Track B — Semantic Intent Classifier:**
* For conversational or conceptual inputs, the input passes through the fine-tuned 66M-parameter classifier to output probability distributions across three operational classes:
1. `SEMANTIC_RAG`: Technical questions, conceptual vulnerability explanations, and multi-hop scenarios requiring deep retrieval.
2. `HARD_REFUSAL`: Obvious out-of-scope queries (e.g., general chit-chat, cooking recipes, sports). The router short-circuits execution and returns `INSUFFICIENT_CONTEXT` immediately, using zero vector search or generation budget.
3. `MALFORMED_INPUT`: Syntactically degraded text, truncated log snippets, or typo-heavy strings routed through string normalization before embedding.

#### 2. Resource & Latency Profile
* **RAM Footprint:** ~150 MB.
* **CPU Execution Time:** ~3 to 5 ms per query on the i7-13620H.
* **Failure Guard:** If the classifier's top softmax probability falls below a threshold ($p < 0.65$), the router defaults safely to `SEMANTIC_RAG` to prevent false-negative drops.
---

### 3. Tier 2: Dense Bi-Encoder (`codefuse-ai/F2LLM-v2-0.6B`)
When a query is classified as `SEMANTIC_RAG`, it passes to Tier 2 to be transformed into a continuous dense vector representation.

#### 1. Why `codefuse-ai/F2LLM-v2-0.6B` Was Selected
Standard text embedding models (e.g., `text-embedding-ada-002` or baseline `bge-small`) are trained predominantly on natural-language prose. They struggle with programming syntax, CVSS vector strings, regex terms, and version operators (`<=`, `rc.1`).
`F2LLM-v2-0.6B` is an open-weights embedding model built specifically for code intelligence, cybersecurity schematics, and enterprise IT text:
* **Base Architecture:** 0.6 Billion parameters (~600M).
* **Native Context Capacity:** 512 tokens.
* **Native Output Dimensions:** 1,024 float32 dimensions.
* **Asymmetric Query/Passage Prefixes:** To maximize retrieval precision between questions and reference chunks, the model uses task-specific instruction prefixes:
* *Query Prefix:* `"Represent this cybersecurity query for retrieving relevant vulnerability and mitigation context: "`
* *Passage Prefix:* `""` (Raw document chunks remain unprefixed to preserve token capacity).

#### 2. Matryoshka Representation Learning (MRL) Vector Truncation
`F2LLM-v2-0.6B` is pre-trained with Matryoshka Representation Learning (MRL). This allows its 1,024-dimensional dense vectors to be truncated to smaller sub-dimensions without retraining:
$$\vec{v}_{1024} = \left[ x_0, x_1, x_2, \dots, x_{511}, \dots, x_{1023} \right] \xrightarrow{\text{Slice}} \vec{v}_{512} = \left[ x_0, x_1, \dots, x_{511} \right]$$
To maintain high similarity fidelity, sliced vectors must be re-normalized using an explicit L2 Euclidean norm:
$$\hat{v}_{512} = \frac{\vec{v}_{512}}{\Vert{}\vec{v}_{512}\Vert{}_2} = \frac{\vec{v}_{512}}{\sqrt{\sum_{i=0}^{511} x_i^2}}$$
* **Memory Savings:** Halves vector width from 1,024 to 512 dimensions, reducing FAISS index memory requirements by 50%.
* **Information Retention:** Benchmark evaluations confirm that 512-dimensional MRL truncation retains **>99.2% of full 1,024-dimensional retrieval accuracy** on technical corpora while doubling SIMD dot-product throughput.
---

### 4. Tier 3: FAISS ScalarQuantizer Index (`IndexScalarQuantizer` SQ8
Once queries are mapped into normalized 512-dimensional vectors, Tier 3 searches the indexed document corpus.

#### 1. Quantization Architecture: SQ8 over Flat or HNSW
Standard uncompressed vector stores use `IndexFlatIP`, storing raw 32-bit floating-point numbers (`float32`). For dense production collections, raw float32 introduces unnecessary cache-line thrashing on CPUs.
Tier 3 uses an **8-bit Scalar Quantizer (`IndexScalarQuantizer` with `faiss.ScalarQuantizer.QT_8bit`)**:
* **Mechanism:** Maps continuous 32-bit floating-point values ($4\text{ bytes}$) into discrete 8-bit unsigned integers ($1\text{ byte}$ per dimension) across uniform scaling intervals:
$$x_8 = \text{round}\left( 255 \times \frac{x_{32} - x_{\min}}{x_{\max} - x_{\min}} \right)$$
* **Memory Footprint:**
$$\text{Memory} = N_{\text{chunks}} \times 512\text{ bytes} + \text{Metadata Overhead}$$
For an indexed corpus of 5,000 chunks, the entire searchable index requires **under 25 MB of system RAM**.
* **AVX2 Acceleration:** FAISS uses Intel Advanced Vector Extensions (AVX2) instructions on the i7-13620H. The processor's 256-bit SIMD registers compute eight 8-bit integer dot products in parallel per clock cycle, searching the index in **under 1 millisecond**.

#### 2. Candidate Retrieval Depth ($K = 8$)
The FAISS index is configured to retrieve the **Top-8 candidate chunks** ($K=8$) per query:
* **Why $K=8$ is the Balanced Choice:**
Setting $K=3$ risks missing relevant context if the bi-encoder misranks chunks. Setting $K=20$ floods the pipeline with irrelevant text and overloads the cross-encoder reranker. Setting $K=8$ provides enough candidate volume to guarantee high initial Recall@8 without slowing down Tier 4.

### 5. CPU Thread Guardrails & Memory Blueprint
To run high-throughput matrix calculations on the i7-13620H without causing thread contention, PyTorch thread pools must be configured explicitly.
```
┌────────────────────────────────────────────────────────────────────┐
│                    PHYSICAL HARDWARE ALLOCATION (TIERS 1, 2, AND 3)                    │
├────────────────────────────────┬───────────────────┬─────────┬─────┤
│ Tier 1: AgentIntentRouter      │ Host CPU (1 Core) │ ~150 MB RAM       │ ~4 ms         │
│ Tier 2: F2LLM-v2-0.6B (MRL 512)│ Host CPU (2 Cores)│ ~1.2 GB RAM       │ ~35 ms        │
│ Tier 3: FAISS SQ8 Index (K=8)  │ Host CPU (AVX2)   │ ~25 MB RAM        │ < 1 ms        │
├────────────────────────────────┼────────┼──────────┼───────────────┤
│ Sub-Part 1.2 Pipeline Total    │ Host CPU (Host)   │ ~1.38 GB Total RAM│ ~40 ms        │
│ Dedicated RTX 4050 6GB GPU     │ CUDA Disabled     │ Exactly 0 MB VRAM │ 0 ms          │
└────────────────────────┴───────────────┴───────────────┴───────────┘

```

#### The Thread Contention Failure Mode
The Intel Core i7-13620H features **16 logical threads** (6 Performance-cores with Hyper-Threading + 4 Efficient-cores).
* By default, PyTorch and OpenMP attempt to grab all 16 threads for every matrix operation.
* Under concurrent loads, multiple incoming queries spawn hundreds of competing threads. The OS scheduler spends more time context-switching between threads than executing vector math, causing query latency to spike from 40 ms to over 800 ms.
* **The Safeguard:** Lock intra-op thread counts to **2 threads** per worker process:
```python
import os
import torch
torch.set_num_threads(2)
torch.set_num_interop_threads(1)
os.environ["OMP_NUM_THREADS"] = "2"
os.environ["MKL_NUM_THREADS"] = "2"
```
This caps CPU utilization cleanly, prevents thread thrashing, and ensures stable P95 response times.

### 2. Tier 4: Cross-Encoder Mechanics (`ettin-reranker-150m-v1`)
Bi-encoders (Tier 2) are limited by vector projection: they compress an entire document into a single fixed-length array independently of the query. Relevant keywords, version numbers, or negation operators can be diluted in dense space. Tier 4 resolves this by processing the query and candidate document through full bidirectional cross-attention.

#### 1. Why `ettin-reranker-150m-v1` Was Selected
* **ModernBERT Backbone:** Built on the ModernBERT-base architecture (unpadding, rotary positional embeddings, GeLU activations), yielding higher inference throughput per parameter than legacy BERT-base models.
* **Parameter Sizing (~149M):** Large cross-encoders (like `bge-reranker-large` at 560M parameters) require 150+ ms per batch on CPU, creating latency bottlenecks. At 149M parameters, `ettin-reranker` executes in **~20 ms on CPU** for 8 candidates while achieving competitive MRR@10 benchmarks on technical datasets.
* **Input Window (8,192 tokens):** Eliminates context truncation concerns when processing token-heavy CVE JSON blocks or lengthy MITRE technique descriptions.

#### 2. Cross-Attention Matrix Interaction
Unlike bi-encoders where similarity is a simple dot product ($\vec{q} \cdot \vec{d}$), the cross-encoder concatenates query and passage into a single sequence separated by a special token:
$$\text{Input} = \text{[CLS]} \, \text{Query} \, \text{[SEP]} \, \text{Candidate Passage} \, \text{[SEP]}$$
Every token in the query attends directly to every token in the candidate passage across all 12 transformer layers. The `[CLS]` token's final hidden state feeds into a binary classification head emitting a raw logit $s_i$, which is passed through a sigmoid function to produce a calibrated relevance score:
$$P(\text{Relevance} \mid Q, D_i) = \sigma(s_i) = \frac{1}{1 + e^{-s_i}}$$

#### 3. Filtering and Context Compression
* **Input Depth:** Receives **$K = 8$** candidate chunks from the FAISS SQ8 index.
* **Relevance Thresholding:** Candidates with a normalized relevance score $P < 0.35$ are discarded as noise.
* **Context Selection:** The top **3 to 5 chunks** ($\sim 1,500\text{ to }2,000$ tokens) are returned. This bounds the prompt size, preventing context dilution and keeping token counts low for both Tier 5 local generation and Tier 6 judge evaluations.
---

### 3. Disentangled Offline Retrieval Metrics
To evaluate retrieval quality objectively before generation, the ranking engine compares retrieved chunk IDs against the `expected_source_chunk_ids` stored in the 150-question golden dataset across four metrics:

#### 1. Recall@k
Measures the proportion of all relevant ground-truth chunks retrieved within the top-$k$ positions:
$$\text{Recall@}k = \frac{\vert{}\mathcal{R}_k \cap \mathcal{G}\vert{}}{\vert{}\mathcal{G}\vert{}}$$
*Where $\mathcal{R}_k$ is the set of top-$k$ retrieved chunks, and $\mathcal{G}$ is the set of expected ground-truth chunks for the query.*
* **Evaluation Purpose:** Essential for multi-hop questions where missing a second or third supporting document causes synthesis to fail.
#### 2. Precision@k
Measures the fraction of retrieved chunks in the top-$k$ that are genuinely relevant:
$$\text{Precision@}k = \frac{\vert{}\mathcal{R}_k \cap \mathcal{G}\vert{}}{k}$$
* **Evaluation Purpose:** Quantifies context clutter. A low Precision@k indicates that irrelevant text is flooding the prompt, which increases generation latency and risks distracting the LLM.
#### 3. Mean Reciprocal Rank (MRR)
Measures where the **first** relevant document appears in the ranked candidate list:
$$\text{MRR} = \frac{1}{\vert{}Q\vert{}} \sum_{i=1}^{\vert{}Q\vert{}} \frac{1}{\text{rank}_i}$$
*Where $\text{rank}_i$ is the position of the first relevant document retrieved for query $i$. If no relevant document is found in the top-$k$, the reciprocal rank is $0$.*
* **Evaluation Purpose:** Validates factual lookups (60 questions) where a single specific CVEor CVSS metric is needed. Target for production: $\text{MRR} \ge 0.85$.

#### 4. Normalized Discounted Cumulative Gain (nDCG@k)
Measures the overall ranking quality, penalizing relevant documents when placed lower down the candidate list:
$$\text{DCG@}k = \sum_{i=1}^{k} \frac{2^{\text{rel}_i} - 1}{\log_2(i + 1)}, \quad \text{IDCG@}k = \sum_{i=1}^{\vert{}\mathcal{G}\vert{}} \frac{2^1 - 1}{\log_2(i + 1)}, \quad \text{nDCG@}k = \frac{\text{DCG@}k}{\text{IDCG@}k}$$
*Where $\text{rel}_i \in \{0, 1\}$ denotes binary ground-truth relevance at position $i$.*
* **Evaluation Purpose:** Verifies that the cross-encoder places the primary context chunk at Rank 1 rather than burying it at Rank 5.
